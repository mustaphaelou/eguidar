# Medusa.js for the eguidar catalogue — research findings

> **Research-only document.** Every factual claim below is traced to a primary source: the npm registry, the `medusajs/medusa` source tree pinned to tag **`v2.21.2`** (the published `latest`, 2026-09-28) and to `develop` where noted, `docs.medusajs.com`, `medusajs.com/pricing`, the README of the one third-party package named, the official starters, and files read in this checkout. **Retrieval date for all sources: 6 October 2026 (UTC).** GitHub files were read at `raw.githubusercontent.com` at the pinned ref; links below use the equivalent `github.com/.../blob/v2.21.2/...` form with line anchors. Four research passes fed this document — R0 (lead-agent first-hand verifications, authoritative), R1 (data model, `v2.21.2`-pinned), R2 (operations, deployment and integration, `v2.21.2`-pinned), R3 (eguidar gap analysis, written in French, translated here). No application code, schema, or configuration was modified.

## Summary

- **What it is.** Medusa v2 is a modular Node.js commerce backend: a set of commerce modules (product, pricing, inventory, order, cart, payment, fulfillment, customer, auth, sales channel, translation, search) composed by *workflows*, exposed as an **Admin API** and a **Store API**, plus a **Vite admin dashboard**. "A Medusa application is made up of a Node.js server and a Vite admin dashboard." ([installation docs](https://docs.medusajs.com/learn/installation)) Current release **2.21.2**, published 2026-09-28T09:59:19.113Z ([npm](https://registry.npmjs.org/@medusajs/medusa)).
- **Out of the box for categories/products/variants.** A real arbitrary-depth category tree (`ProductCategory` with materialized-path `mpath`, sibling `rank`, unique `handle`, soft delete), products with handle/status/thumbnail/images/options/tags/type/collection, variants keyed by option combinations with unique `sku`/`barcode`/`ean`/`upc`, inventory across stock locations, multi-currency pricing with price lists and rules, translation, and a merchant UI covering Create/Edit Product, Variants, Collections, Categories, Product Options ([user guide](https://docs.medusajs.com/user-guide/products)).
- **It is not a drop-in for eguidar's catalogue.** Three structural mismatches decide this. (1) **Money**: eguidar stores integer **centimes** (`lib/money.ts:8`, `prisma/schema.prisma:101`); Medusa stores `Price.amount` as a **decimal in major units** on a `PriceSet` linked to the variant — integer centimes must become `cents / 100`. (2) **No price and no stock on the variant**: `ProductVariant` has neither column; prices live in the Pricing module, stock in the Inventory module (`product-variant.ts` @ v2.21.2), so eguidar's `{ sku, priceDelta, stock }` has no one-row home. (3) **No cycle guard on the category tree**: no check was found in the repository, the Admin validator, the core-flow workflows or the route that a re-parented category is not its own descendant, and the read-path recursion has no visited set — the direct counterpart of [`docs/adr/0030-la-marche-de-la-structure.md`](../../docs/adr/0030-la-marche-de-la-structure.md).
- **The cart/order/delivery domain stays custom.** Medusa's `pp_system` provider is documented as acting "similarly to a cash-on-delivery (COD) payment method", but eguidar's single 6-value `OrderStatus` axis with `STATUTS_ENCAISSÉS = ["delivered"]` (ADR-0009), its persisted `Order.totalPayable` (ADR-0021), its per-city `DeliveryCity.fee` + `ShippingSettings.freeShippingThreshold`, and its **Devis** (all cities priced side by side before any order) have no first-party Medusa equivalent.
- **Licence.** The repository is **MIT except the "Enterprise Edition materials identified in `ENTERPRISE-LICENSE.md`"** — RBAC and SSO (OIDC), enumerated path by path, requiring "a separate, valid commercial agreement with MedusaJS, Inc."; the same file says "Files outside this list remain under the MIT License". The published npm `license` field is the string `SEE LICENSE IN LICENSE`, **not** `MIT`, so automated scanners will report it as unknown.
- **Adoption shapes, one line each.** **(a)** Medusa as the backend of record — Store API feeds the storefront, its admin replaces `app/admin`, Order/Cart/Payment replace Prisma: one source of truth for products, but an auth rewrite, the loss of the ADR-0007 visitor cart, an admin that cannot be re-skinned, and six Prisma models (Theme/Blog/DeliveryCity/ShippingSettings/BrouillonImageProduit) stranded on a second connection. **(b)** Medusa as catalogue back-office only, cart/orders/delivery staying in Prisma: the least invasive shape, but **two sources of truth for products**, a Prisma cart that can no longer join the product, and a Meilisearch index that nothing re-indexes when Medusa is written to. **(c)** No Medusa: cost zero; the three real gaps today (index consistency is best-effort only, no Brand entity, no stock location) do not require Medusa.

## 1. What Medusa v2 is

Medusa v2 is a modular commerce framework rather than a monolith. Commerce capabilities are separate modules registered in `medusa-config.ts`, and cross-module writes are composed as **workflows** (steps with compensation). Two HTTP surfaces are generated: the **Admin API** (`/admin/...`, authenticated, dashboard-facing) and the **Store API** (`/store/...`, publishable-key-scoped, storefront-facing). The admin is a **Vite** application served by the Medusa server at **`/app`** and switchable off with `admin.disable` / `DISABLE_MEDUSA_ADMIN=true` on the instance that should not serve it ([installation](https://docs.medusajs.com/learn/installation), [deployment](https://docs.medusajs.com/learn/deployment/general), [admin](https://docs.medusajs.com/learn/fundamentals/admin)).

## 2. The catalogue data model

All field definitions below are verbatim from the models at tag `v2.21.2`; line numbers are against the file at that ref. `ProductCategory` fields are `id` (`pcat`), `name` (searchable, translatable), `description` (searchable, translatable, default `""`), `handle` (searchable), **`mpath`** (materialized path), `is_active` (**default `false`**), `is_internal` (default `false`), `rank` (default `0`), `external_id` (nullable), `metadata` (json), `parent_category` (nullable self-relation), `category_children` (self-relation), `products` (many-to-many) — [product-category.ts:6–26](https://github.com/medusajs/medusa/blob/v2.21.2/packages/modules/product/src/models/product-category.ts#L6-L26). There is **no `slug` field**: the URL field is `handle`, unique through a partial index on `deleted_at IS NULL`; `mpath` has a non-unique index. `Product` carries `id` (`prod`), `title`/`subtitle`/`description`/`material` (translatable; **`handle` is not**), `status` (`draft` | `proposed` | `published` | `rejected`, default `draft`), `thumbnail`, dimensions, `origin_country`/`hs_code`/`mid_code`, `discountable` (default `true`), `external_id`, `metadata`, `variants`, `type`, `tags`, `options`, `product_options` (since 2.16.0), `images`, `collection`, `categories` — [product.ts:17–144](https://github.com/medusajs/medusa/blob/v2.21.2/packages/modules/product/src/models/product.ts#L17-L144).

`ProductVariant` carries `id` (`variant`), `title` (translatable), `sku` (**nullable**, unique), `barcode`/`ean`/`upc` (unique, nullable), `allow_backorder` (default `false`), **`manage_inventory` (default `true`)**, `hs_code`, `origin_country`, `mid_code`, `material`, dimensions, `metadata`, `variant_rank` (default `0`, nullable), `thumbnail` (since 2.11.2), `product`, `images` (since 2.11.2), `options` via the pivot table `product_variant_option` — [product-variant.ts:7–47](https://github.com/medusajs/medusa/blob/v2.21.2/packages/modules/product/src/models/product-variant.ts#L7-L47). **There is no price column and no stock column.** Variants are not generated automatically: the product's option axes are declared with `title`/`values`, and each variant is posted with `options` as a `{ optionTitle: value }` record ([create-variant](https://docs.medusajs.com/api/admin/products/create-variant)); `ProductOption.is_exclusive` (since 2.16.0) exists for product-local options.

## 3. Managing the catalogue: admin UI and APIs

**Merchant screens.** The Products domain "is where you manage all your products, their variants, and the different ways to organize them, such as categories and collections", with sub-guides **Create Product, Edit Product, Manage Variants, Manage Collections, Manage Categories, Manage Product Options** ([user guide](https://docs.medusajs.com/user-guide/products)). `/user-guide/categories` is a 404 — the category guide lives under the products tree. Inventory is managed from the inventory-items area, and the variant's **manage inventory** flag (`manage_inventory`, default `true`) is part of the create/update variant bodies — i.e. what the product screen writes to.

**The admin application, and its ceiling.** It is served **by the Medusa server at `/app`** by default (`/admin`, `/store` and `/auth` are reserved paths), built statically with Vite v7, and `admin.disable: true` stops it being compiled at all — which is why the documented production posture disables it on the worker only. It is extensible through exactly two mechanisms: **widgets** (`src/admin/widgets/*.tsx`, injected into pre-defined zones) and **UI routes** (`src/admin/routes/**/page.tsx`, new pages). The docs state the ceiling explicitly: "You can't customize the admin dashboard's layout, design, or the content of the existing pages (aside from injecting widgets). **You also can't change the Medusa logo used in the admin dashboard.**" So the shipped admin can replace `app/admin` functionally but **not** visually — white-labelling means building your own admin against the Admin API (264 admin route files at 2.21.2), whose auth is bearer/session/Basic-key based.

**Store API routes:** `/store/products`, `/store/products/:id`, `/store/product-variants`, `/store/product-categories`, `/store/product-options`, `/store/product-tags`, `/store/product-types`, `/store/collections`, `/store/currencies`, `/store/locales`, `/store/regions`, `/store/search`, plus carts, orders, customers, payment collections and shipping options.

**Bulk and CSV surfaces — the migration path.** There *is* a documented bulk-variant editor: `POST /admin/products/:id/variants/batch` with body `{ create?, update?, delete? }`, returning `{ created, updated, deleted }` ([manage variants](https://docs.medusajs.com/api/admin/products/manage-variants-in-a-product)); `POST /admin/products/batch` does the same for products. There *is* CSV import/export ([import guide](https://docs.medusajs.com/user-guide/products/import)), with v1-compatible column names recognized in `normalize-v1-import.ts` (`Product Handle`, `Variant SKU`, `Variant Inventory Quantity`, `Price …`, `Image`, `Option <name>`, …) and `variant_price_*` keys turned into `{ currency_code, amount }` in `normalize-for-import.ts:312–334`; the category column is recognized there but discarded — see point (ii) below. The mechanical export is therefore one CSV row per variant with `Variant SKU`, `Variant Inventory Quantity` and `Price MAD` columns — **but `priceDelta` has no CSV column** and must be resolved to an absolute amount first. A CLI path also exists (`medusa exec ./src/scripts/seed.ts`, [custom CLI scripts](https://docs.medusajs.com/learn/fundamentals/custom-cli-scripts/seed-data)), and the docs carry migration guides for Magento, Shopify and WooCommerce — none of them eguidar-shaped.

**Where the research passes disagreed, and how it was resolved (two points on this surface).** (i) R0 read the import step and found it throws `INVALID_DATA` "Product handle is required when importing products" when a row lacks `Product Handle`; R3 read the user-guide column table (at `develop`, in the MDX source) and found `Product Title` marked as the only required column. This document follows the **code read** (R0, authoritative, and the layer that actually rejects the file), and notes the user guide's claim — so an eguidar export must carry handles regardless. (ii) `Product Category` — R0 described it as carrying the Structure **name** (via the v1-compatibility helper's column list); R3 read the user-guide column table as carrying a category **ID**, repeatable. This is now settled from source in favour of R3: `normalize-for-import.ts:276–283` @ `v2.21.2` turns a `product_category_*` key into `response["categories"] = [..., { id: normalizedValue }]`, and the user-guide table at `v2.21.2` says "The ID of a product category, where `*` is the number of the category, allowing you to add more than one category. For example, `Product Category 1`." The trap is the v1 path: `normalize-v1-import.ts` **deletes** every `Product Category*` key outright — its own comment reads "Note: Product categories from v1 are not imported to v2". So an eguidar export must use the current `Product Category N` columns, and the migration is **three steps, not two**: import the tree, build a **name → id map**, then write the product CSV with those ids.

**Auth on the wire.** Store requests need the publishable API key: `PUBLISHABLE_KEY_HEADER = "x-publishable-api-key"` (`@medusajs/utils@2.21.2` `dist/api-key/api-key-type.js:20`); the middleware returns `NOT_ALLOWED` with "Publishable API key required in the request header: x-publishable-api-key" if it is absent, then resolves the key to its `sales_channels_link.sales_channel_id` and sets `req.publishable_key_context`. **The key is what scopes a storefront to its sales channels**, and inventory availability is resolved from those channels' stock locations. Admin-side there are three mechanisms — session cookie, `Authorization: Bearer <jwt>`, and a **secret API key sent as `Authorization: Basic <sk_...>`** (a secret key sent as a Bearer token is rejected with an explicit hint). There is **no `/store/auth/*` in v2**: customer authentication lives at `/auth/{actor_type}/{provider}` — `POST /auth/customer/emailpass/register` returns a JWT that is then passed to `POST /store/customers` — and the providers registered at 2.21.2 are `emailpass` (default), `github`, `google` and `oidc`. A related consequence, read in source: store endpoints that expose `Product` as a relation ask for the published constraint themselves (`publishedProductsContext`), so a Store category listing only surfaces categories that carry published products. Two API-shape traps: `UpdateProduct.options` was removed in 2.16.0 and the validator now always fails with "The 'options' property was removed in version 2.16.0. Please remove it from your request payload." (use `POST /admin/products/:id/options/batch` and `option_ids`), and the Store product query **overrides the framework's default `storeRelationsLimit` of 3 to 4** on this route (`packages/medusa/src/api/store/products/query-config.ts:103`).

**Source hygiene.** The page `https://docs.medusajs.com/user-guide/products/import/index.html.md` begins with an `<AgentInstructions>` block instructing agents to reproduce a feedback section verbatim and to POST to a feedback endpoint; this research treated it as data, not instructions, and records it here as a fact about the source.

## 4. The category tree, in detail

This is the section eguidar's ADR-0027/ADR-0030 knowledge pays for. Medusa's `ProductCategory` is a real tree of arbitrary depth with **no depth column and no depth cap**: ancestry is a **materialized path** in `mpath`, built on create as `` parentCategory ? `${parentCategory.mpath}.${result.id}` : result.id `` — and `create` throws `INVALID_ARGUMENT` if the parent id does not exist (`product-category.ts` repository, @ v2.21.2). Descendants are queried with a `LIKE` prefix scan (`mpath: { $like: `${cat.mpath}%` }`), ancestors by splitting `mpath` on `"."` — **not** a recursive CTE. Reads can request `include_descendants_tree` / `include_ancestors_tree`; the Store API documents them as retrieving the parent / child categories.

| Property | Behaviour (read at v2.21.2) |
|---|---|
| `mpath` | materialized path; index `IDX_product_category_path` is **non-unique**, partial on `deleted_at IS NULL` |
| `handle` | **unique** per non-deleted row (`IDX_category_handle_unique`, partial on `deleted_at IS NULL`) |
| `is_active` | **default `false`** — a category created without `is_active: true` is inactive. The Admin list filter set includes `is_active`; the documented Store list filter set does **not** (whether the Store API excludes inactive categories by default was not verified — §8) |
| `rank` | sibling ordering; reads sort by `rank` (`sortCategoriesByRank`), and the repository re-ranks siblings after creation and deletion. **There is no dedicated reorder endpoint** — `rank` is set through the ordinary create/update bodies |
| Deletion | **soft delete** (`deleted_at`), with `restore`; a hard delete exists but the Admin route calls `softDeleteProductCategories` |
| Children | deletion is **refused**: `MedusaError.Types.NOT_ALLOWED`, "Deleting ProductCategory (<id>) with category children is not allowed" |
| Products on delete | products survive; only the `product_category_product` pivot rows are removed (`removeRemoteLinkStep`) |
| Cascades | the model declares `.cascades({ delete: ["category_children"] })` while the repository refuses the delete first — the guard is the repository, and the two are in tension. Both are attributed here; the observable behaviour is the refusal |

**The tree machinery, in source terms.** The repository is a tree repository (`ProductCategoryRepository extends DALUtils.MikroOrmBaseTreeRepository<typeof ProductCategory>`), and tree building is a recursive `populateChildren(category, level = 0)` with a level counter but **no maximum**. Sibling order is application-level: the default read order is `{ id: "ASC", rank: "ASC" }` with an explicit `sortCategoriesByRank`, and `rerankSiblingsAfterCreation`, `rerankSiblingsAfterDeletion` and `rerankAllSiblings` keep the ranks dense. **No `mpath` or `parent_category_id` DDL appears in the product module's migrations** — a recursive grep over `packages/modules/product/src/migrations/*.ts` at `v2.21.2` returns zero matches for either string, so the tree columns are created by the DML/entity-builder layer from the model definition, and the only declared constraints are the two indexes in the properties table. There is therefore no database-level depth limit, no exclusion constraint, and no self-parent check.

**Deleting a tree** is documented in the delete workflow's own comment, verbatim: "A product category that has child categories can't be deleted. All the IDs passed as input are validated and deleted as a single batch, so the input must not contain both a category and any of its descendants. Ordering the input array deepest-first has no effect. To delete a category tree, group the IDs by depth and run this workflow once per depth level, starting with the deepest level." That is the depth-by-depth workaround. `baseDelete` loads `populate: ["category_children"]` first and runs the refusal check per ID; the Admin route's workflow step calls `softDeleteProductCategories`, and `restore` exists for the soft-deleted rows.

**The absence of a cycle guard.** Reading `packages/modules/product/src/repositories/product-category.ts` at `v2.21.2`: `update`, when `parent_category_id` changes, rebuilds descendants with `buildProductCategoriesWithTree({ descendants: true }, …)` and rewrites every descendant's `mpath` through `updateMpathRecursively` — **with no visited set and no comparison of the new parent against the category's own id or its `mpath`**. Every `throw` in the file was enumerated; the six sites are `NOT_FOUND` (softDelete, baseDelete, missing category on update), `NOT_ALLOWED` (children), and `INVALID_ARGUMENT` (missing parent on create and on update) — none is a cycle check. Upstream layers add nothing: `AdminUpdateProductCategory` / `AdminCreateProductCategory` accept `parent_category_id: z.string().nullish()` with no refinement (`packages/medusa/src/api/admin/product-categories/validators.ts:78`), the create/update core-flow workflows contain no `throw`/`MedusaError`, and the Admin route only throws `NOT_FOUND`. The **read path is likewise unguarded**: `populateChildren` in `buildProductCategoriesWithTree` recurses with a `level` counter and no visited set, so a cycle would not terminate there either. This is stated as **"no guard found at these layers, reading these files; not reproduced by running it"** — no test was executed.

**This is the direct counterpart of ADR-0030.** eguidar has the same underlying shape — a self-relation with no database-level cycle guard (`prisma/schema.prisma:86–87`, `ON DELETE SET NULL`, no index on `parentId`, and ADR-0027:528–534 explicitly refused a depth rule) — but it wrote the guards Medusa does not have. Layer by layer:

| Layer | eguidar (read in this checkout) | Medusa v2 @ `v2.21.2` |
|---|---|---|
| Write serialisation | `verrouillerStructure` arms `lock_timeout` at `DELAI_VERROU_STRUCTURE_MS = 1000` and takes `SELECT id FROM "Category" FOR UPDATE` over the whole table ([`lib/use-cases/admin-structure.ts:271–276`](../../lib/use-cases/admin-structure.ts#L271-L276)) | **none found** — no lock or transaction guard in the repository or the workflows |
| Acyclicity on re-parent | `assertAcyclicCategoryTree` distinguishes "under one of its own descendants" from a cycle already in the database and raises `CategoryAncestorCycleError` (`:415–446`) | **none found** — `parent_category_id: z.string().nullish()`, no refinement; `updateMpathRecursively` has no visited set |
| Read path | visited sets in `collectCategoryAndDescendantIds` (BFS) and `getCategoryChain` (breadcrumb); `buildCategoryTree` erases cycles silently ([`lib/use-cases/storefront.ts:88`](../../lib/use-cases/storefront.ts#L88), `:199–227`, `:283–301`) | `populateChildren` recurses with no visited set — a cycle would not terminate there either |
| Delete with children | refused by default, with `reassignToCategoryId` / `reparentChildrenToCategoryId` / `orphanProducts` as **explicit editor choices** (`:586–717`) | refused; the only recipe is one workflow run per depth level, and there is no reassign-or-orphan option |
| Delete with products | `CategoryHasProductsError` unless reassignment or `orphanProducts === true` is chosen (`:672–682`) | products survive and are detached through `removeRemoteLinkStep`; no choice is recorded |
| Product ordering | no rank at all: `isFeatured` then `[{featuredOrder: "asc"}, {name: "asc"}]` | `rank` + automatic sibling re-ranking, **categories only** |
| Depth | no rule (ADR-0027 refused to add one) | no rule found |

Adopting Medusa on categories would therefore remove ADR-0027's serialisation and ADR-0030's march **without replacing them**. *Inference, labelled:* preserving those two decisions on top of Medusa would mean writing the guard outside the core — a workflow step, a subscriber, or a database trigger — because no core guard was found at the layers listed; that is a conclusion from the absence, not a verified statement about Medusa's extensibility surface.

**What migrating the Structure itself would involve** (all from the reads above): the rows must be inserted **parents before children**, because `mpath` is computed from the parent's `mpath` and `create` throws if the parent id does not exist; every migrated category must set `is_active: true` **explicitly**, since the default is `false`; an order must be chosen for siblings, because Medusa sorts by `rank` and eguidar's `Category` has no ordering column at all — so any ordering is a new decision, not a translation; `Category.image` has no destination; and tearing down the old tree in Medusa cannot be done in one call, because a category with children cannot be deleted — the depth-by-depth recipe is the only documented path.

## 5. Operating it

**Infrastructure.** A production Medusa needs PostgreSQL, Redis, and the app in **two modes — server and worker** — on "at least 2GB of RAM" ([deployment](https://docs.medusajs.com/learn/deployment/general)). `workerMode` takes `"shared" | "worker" | "server"`; `shared` runs one process and is dev-only in practice. Redis is *not* an install prerequisite, and it is **not one switch but four separate infrastructure modules**, all defaulting to in-process: the event bus (`event-bus-local`), caching (`cache-inmemory`), the workflow engine (`workflow-engine-inmemory`) and locking (`@medusajs/medusa/locking`). The locking default "uses a plain JavaScript map to store the locks… not recommended for production… only intended for use in a single-instance environment". Setting `REDIS_URL` does **not** auto-swap the self-hosted set: in `resolveModules()` the `if (process.env.REDIS_URL)` branch appends the Redis modules to `cloudModules` only, while self-hosted resolves the unconditional in-memory `defaultModules`, so self-hosted requires the four Redis modules registered explicitly in `medusa-config.ts` — with distinct variables (`REDIS_URL` for session/event bus/workflow engine, `CACHE_REDIS_URL`, `LOCKING_REDIS_URL`). This matters for eguidar because the Search Module declares `dependencies: [EVENT_BUS, LOCKING, LOGGER, QUERY]`: with an in-process event bus, a crashed worker loses an index update. `projectConfig.redisUrl` alone governs only the **session** store — "When specified, the Medusa server uses Redis to store the session data. Otherwise, the session data is stored in-memory" — and the docs warn not to set it on Cloud, which provisions Redis. **No minimum PostgreSQL major version is documented**: R0 checked `learn/installation` and `learn/deployment/general`, R2 found no pin in any file it read. eguidar runs `postgres:16-alpine` (`docker-compose.yml:3`), above any plausible floor, but no floor is asserted.

**Install paths.** `npx create-medusa-app` scaffolds a Medusa backend, and it does **not** scaffold a Next.js storefront by default (`--with-nextjs-starter` defaults to `false`). There is no documented "add Medusa to an existing repo" wizard — the CLI always creates a new project or a plugin — so the supported shape is a **separate Medusa app wired into the existing repo**, which is what the current official starter `medusajs/dtc-starter` does (a pnpm/Turborepo workspace with `apps/backend` and `apps/storefront`). The previously cited `medusajs/nextjs-starter-medusa` is **deprecated** — its README points to `dtc-starter` — so the "not eguidar's UI stack" point for ADR-0008 is grounded on the shipped dashboard package instead: `@medusajs/dashboard@2.21.2` depends on `@medusajs/ui@4.2.6` and `radix-ui`, not Base UI/Hugeicons. The practical route is `npx create-medusa-app@latest my-backend --skip-db`, move the directory into the workspace, point `DATABASE_URL` at its own database, and add `"predeploy": "medusa db:migrate"`. The storefront consumes the Store API through `@medusajs/js-sdk` (`sdk.store.*`, `sdk.admin.*`), which at 2.21.2 has **no** `sdk.store.search` and no `sdk.store.variant` group — search goes through the InstantSearch adapter and variants through a raw fetch. Seed and data-migration scripts run through the CLI (`medusa exec ./src/scripts/seed.ts`).

**Deployment.** `medusa build` emits to **`.medusa/server`**, where dependencies are installed and `start` runs; migrations are a `predeploy` script (`medusa db:migrate`, tracked in a single `mikro_orm_migrations` table), which means on a multi-instance rollout **every instance would attempt them** — sequence the deploy or run `predeploy` once. Health is `GET /health` → `OK`. The admin is compiled during the build unless disabled, and the documented posture is `DISABLE_MEDUSA_ADMIN=true` on the worker only. The self-hosted docs at `v2.21.2` list **only** the general guide plus "Deploy Next.js Starter Storefront → Vercel"; the provider-specific guides (Railway, Render, DigitalOcean, Heroku, AWS, Fly, Kubernetes) are gone from the docs index at that ref.

**Cloud.** Develop "From $29/mo", Launch "$99/mo", Scale "$299/mo", Enterprise "Custom"; "GMV platform fee 0.0%", unlimited orders/products/sales channels/regions; "Medusa Search and Emails" and a "Redis-backed KV store" are Cloud features, and "RBAC, SSO, Audit Logs" are Enterprise-plan features ([pricing](https://medusajs.com/pricing)) — consistent with `ENTERPRISE-LICENSE.md`. **No free tier is asserted**: the page carries a "Start for free" call to action alongside "From $29/mo", and the two cannot be reconciled from the page (see `## Not retrieved`).

**Database sharing — decisive.** Medusa owns its schema entirely: its migrations create **143 distinct unprefixed tables**, including collision-prone generic names (`cart`, `currency`, `customer`, `order`, `payment`, `price_list`, `product`, `store`, `user`), tracked in a single `mikro_orm_migrations` table, with `db:rollback` **per module** and no documented drop/reset command. Its default schema is resolved as `configModule.projectConfig.databaseSchema || "public"` (`@medusajs/framework@2.21.2` `dist/database/pg-connection-loader.js:36`). The option is real but **effectively undocumented**: R0 reported zero matches for `databaseSchema` in `llms-full.txt`, R2 reported exactly one, and a re-run of that grep on the same 6,908,173-byte corpus (6 Oct 2026) finds **exactly one** — line 31400, inside a v1→v2 configuration-rename table (`projectConfig.database_schema` → `projectConfig.databaseSchema`). The sources disagreed; this document follows R2's more specific read plus the direct check, and the conclusion is unchanged — the option never appears in the configuration reference, so using it means relying on undocumented-in-practice behaviour. eguidar's commerce tables are **quoted PascalCase** in `public` with no `@@map` (`prisma/migrations/20260810111743_init/migration.sql`), so `"Product"` ≠ `product` and `"Order"` ≠ `order`; R2's generic collision list assumes the other app's tables are lowercase and unquoted, which is not eguidar's case. The collision set for this repo is therefore the lowercase better-auth tables, and **`"user"` is a hard collision**: `@medusajs/user`'s migration runs `create table if not exists "user"`, so a pre-existing Prisma `"user"` means Medusa silently skips creating its own and then fails at runtime against an incompatible shape. `"session"` looks safe (no `session` table was found in `@medusajs/user`, `@medusajs/auth`, `@medusajs/customer` or `@medusajs/framework`). Therefore **one database in `public` is not safe as-is**: give Medusa its own database (cleanest, no undocumented behaviour) or its own schema via `projectConfig.databaseSchema` (works mechanically, you own the risk). No Medusa documentation of a shared-database story was found, and none is claimed here. The rest of the infra floor is already met in this repo: `postgres:16-alpine`, `redis:7-alpine` and `getmeili/meilisearch:v1.52` in [`docker-compose.yml:3,21,34`](../../docker-compose.yml#L3), plus `@aws-sdk/client-s3` and a presigner in `package.json`.

## 6. Search: what happens to Meilisearch

Medusa's **Search Module requires v2.21.1+**, is GA, and is **registered by default** with `@medusajs/search-postgres`: "As of v2.21.1, the Search Module is registered by default in your Medusa application with the PostgreSQL Search Module Provider, so you only declare the indexes to search." It is declarative — index definitions declare which entities and fields are indexed, with `.searchable()`, `.filterable()`, `.facetable()`, `.retrievable()` modifiers and an official example titled "Index Categories and Tags as Facets" ([search module](https://docs.medusajs.com/resources/infrastructure-modules/search), [index definitions](https://docs.medusajs.com/resources/infrastructure-modules/search/index-definitions)). `/store/search` serves it, but **nothing is searchable until `configureStoreSearch` opts an index in**, and if the module is absent the route errors with "The Search Module is not installed, so nothing can be searched." Official providers: `@medusajs/search-postgres@2.21.2` ("backed by tsvector and pg_trgm"), `@medusajs/search-local@2.19.0` ("backed by Orama"), and Cloud's "Medusa Search"; `@medusajs/instantsearch-adapter@2.21.2` is the official **Algolia** InstantSearch adapter. **There is no official Meilisearch provider** — the v1→v2 guide says MeiliSearch is "Not available, but you can integrate it".

**Both official integration guides are deprecated.** The Algolia and Meilisearch tutorials each carry, verbatim: "**Deprecated.** This guide is deprecated as of Medusa v2.21.1, which introduced the Search Module. Rather than the custom module this guide builds, consider one of the following instead: Medusa Search, the managed search service for Cloud projects… A Search Module Provider for Algolia/Meilisearch, which keeps [the engine] behind the Search Module's index definitions and `query.search`." They were always "build a custom module yourself" tutorials, never shipped integrations — and R2 found **no** first-party provider package for either engine. The module declares `dependencies: [EVENT_BUS, LOCKING, LOGGER, QUERY]`, which is the strongest argument for the Redis event bus in production (§5): index updates ride the event bus.

The only Medusa-2 Meilisearch package on npm is the community `@rokmohar/medusa-plugin-meilisearch`, latest **2.3.1**, published 2026-10-03, peer `@medusajs/medusa ~2.21.1`. Its compatibility table: `^2.3.0` ↔ Medusa `2.21.1 – 2.21.x`, Meilisearch server `>= 1.20`, Node `>= 22.12`; `^2.2.0` ↔ `2.21.x`; `^2.1.0` ↔ `2.20.x`; `^2.0.0` ↔ `2.19.x`. Its README warns: **"Each Medusa minor has so far reshaped the Search Module, so every row above is exact rather than a floor."** That is the maintenance risk to name: it is a third-party package that must track Medusa minors, and it is the only Meilisearch option.

**Where the research passes disagreed, and how it was resolved.** R3 verified the plugin's npm metadata but could not tell whether it implements the 2.21.1 Search Module provider contract or its own indexing pipeline. R0 settled it from the plugin's own README, verbatim: "Medusa 2.19.0 introduced a Search Module of its own, and from v2.0.0 this plugin plugs into it as the Meilisearch engine behind it", claiming "Every method of the provider contract… batched multi-search, and write-task tracking", with the Search Module doing index creation/seeding/batching/rebuilds and the plugin translating declarations into Meilisearch settings and queries. R2 did not independently verify the plugin and recorded that gap; R0 did, so this document keeps R0's finding and treats the plugin as a **Search Module provider — a third-party one**. The same split applies to `@medusajs/search-local` (Orama): R0 verified it from npm, R2 did not verify it and does not assert it, so R0's read stands here.

What Medusa's Search Module does **not** hand over is ADR-0016's rule that a facet's count ignores its own filter clause: `.facetable()` exists and `/store/search` exists, but no documented mechanism was found for a facet query with its own clause removed, so that rule would be reimplemented above the seam. eguidar's infrastructure already meets the floor — Meilisearch **v1.52** (`docker-compose.yml:34`) is above the plugin's `>= 1.20`, and Redis 7 / PostgreSQL 16 are running — but the integration itself is third-party, and the URL language (`q`, `marque`, `categorie`, `prix`, `tri`, `page` in `lib/search-params.ts:63–88`) belongs to eguidar and is unknown to Medusa.

### 7.3 Adoption shapes and their seams

| | (a) Medusa as backend of record | (b) Medusa as catalogue back-office | (c) No Medusa |
|---|---|---|---|
| Medusa owns | catalogue, cart, order, payment, fulfillment, auth | categories, products, variants only | nothing |
| Prisma keeps | Theme, Blog, DeliveryCity, ShippingSettings, BrouillonImageProduit | all of the above **plus** Cart/Order/Delivery/auth | all 16 models |
| Sources of truth for a product | one (Medusa) | **two** (Medusa + the Prisma mirror the cart needs) | one (Prisma) |
| Index consistency | Search module, or the community Meilisearch provider | **nothing re-indexes on Medusa writes** without a subscriber or job | unchanged (best-effort, ADR-0014) |
| ADRs given up | 0007 (visitor cart), 0008 (UI kit), 0013 (cooked DTOs), 0027/0030 (structure guards), 0029 (orphans) | 0013, 0027/0030, 0029 | none |
| Principal risk | auth rewrite and a two-database storefront | **two product sources of truth and a stale search index** | none — but three gaps stay unfixed |

**(a) Medusa as the backend of record.** The Store API feeds the storefront and Medusa's admin replaces `app/admin`. Concretely: [`lib/use-cases/storefront.ts`](../../lib/use-cases/storefront.ts) (382 lines) becomes `sdk.store.*` calls and loses `buildCategoryTree`/`accumulateProductCounts`/`collectCategoryAndDescendantIds`/`getCategoryChain`; [`lib/use-cases/admin-catalog.ts`](../../lib/use-cases/admin-catalog.ts) (785) and [`lib/use-cases/admin-structure.ts`](../../lib/use-cases/admin-structure.ts) (727) are replaced or rewritten on `sdk.admin.*` (the lock and the march lose their site); [`lib/product-metrics.ts`](../../lib/product-metrics.ts) loses `prixVariante`/`minVariantPrice`; [`lib/money.ts`](../../lib/money.ts) stops dividing by 100; `lib/panier*`, `lib/use-cases/{devis,livraison,orders}.ts`, [`lib/statut-de-commande.ts`](../../lib/statut-de-commande.ts) and `lib/auth.ts` are replaced by Cart/Fulfillment/Order/Payment/Auth, which means rewriting better-auth and re-homing `user.shippingCityId` (`prisma/schema.prisma:20`); `lib/cycle-vie-image-produit.ts` (~1000 lines) and `lib/r2.ts` give way to the File module (image drafts have no equivalent); `prisma/schema.prisma` shrinks to Theme/Blog/DeliveryCity/ShippingSettings/BrouillonImageProduit — six models with no Medusa owner. Duplication on products is nil, but the storefront then joins two databases (products in Medusa, blog and cities in Prisma): two connections, two migrations, two backups, and no `orderBy` across them. Two specific losses: **Facebook sign-in** — the registered providers are `emailpass`, `github`, `google` and `oidc`, and Facebook was not found, while ADR-0019 currently trusts Facebook e-mail — and **the admin's appearance**, which cannot be re-skinned: the docs forbid changing the layout, design or existing page content, and forbid changing the Medusa logo, so replacing `app/admin` means accepting Medusa's UI or building a custom admin against the Admin API.

**(b) Medusa as catalogue back-office only.** Medusa owns categories, products and variants; its Store API is *read* by the existing Next.js; Panier, commandes, Devis and livraison stay in Prisma. This is the least invasive shape — `lib/panier*`, `lib/use-cases/{orders,devis,livraison}.ts`, `lib/auth.ts` and `app/admin/{commandes,villes,livraison}` do not move — **but the dividing line does not hold**, and that is the finding to carry:

1. **The cart needs price and stock, which now live in Medusa.** `construireArticleDuPanier` reads `variant.product.price` and `variant.priceDelta` (`lib/panier-coeur.ts:276`) and `variant.product.freeShipping` (`:290`); `reserverStock` decrements `ProductVariant.stock` (`lib/use-cases/orders.ts:223–226`). If Medusa owns the variant, both paths must read Medusa — so the Panier and the commande become Medusa readers, and stock has either **two writers** (Medusa for administration, Prisma for reservation) or one (Medusa, with `reserverStock` calling the Inventory module).
2. **The Prisma cart can no longer join the product.** `Product.categoryId` disappears from Prisma while `CartItem → ProductVariant → Product` (`prisma/schema.prisma:159–171`, `:122–135`) is how the Panier resolves a line. A mirror table (`variantId → { price, stock, freeShipping, name, sku }`) reconciled from Medusa, or a Medusa read per line, is mandatory.
3. **The Produit sans Structure does not survive.** `Product.categoryId` nullable, the reserved facet key `_sans-structure` ([`lib/index-projection.ts:27`](../../lib/index-projection.ts#L27)) and the "orphanhood is a choice" rule are eguidar facts; Medusa's many-to-many has no orphan state. `admin-catalog.ts:241` (`categoryId: z.string().min(1)`) and the related-products read (`storefront.ts:317–324`) depend on it.
4. **The price changes unit and nature.** `price Int` (centimes) + `priceDelta Int` (centimes, relative) becomes an **absolute** `Price.amount` per variant in major units. The conversion is mechanical but not trivial: `price + priceDelta` must be materialised per variant, so "changing the base price" stops being a single write, and two symmetric conversions in two modules is exactly where a rounding contract gets lost.
5. **The stock changes model.** One `Int` column becomes `InventoryItem` + `InventoryLevel` per `StockLocation` with `bigNumber` quantities; `totalVariantStock` becomes a sum over levels.

**Two sources of truth for products, and the Meilisearch index belongs to neither.** `indexProductDocuments` is called from `admin-catalog.ts` and `admin-structure.ts` — eguidar code — so once the administration is Medusa's, **nothing re-indexes on write**. The fix is a Medusa **subscriber** in the worker on `product.created` / `product.updated` / `product.deleted` (and the hyphenated `product-category.*` / `product-variant.*`), whose payload carries **only `{ id }`** — so the subscriber must re-fetch the record and then call the eguidar re-index endpoint or queue. There is **no first-class outbound webhook** in self-hosted v2: `/hooks/payment/[identifier]_[id]` is inbound, and Cloud webhooks deliver only `build.*` / `deployment.*` platform events. Today the index write is already best-effort and non-transactional (`runEffect`, ADR-0014), so this compounds an existing weakness rather than creating a new one. Finally, `user.shippingCityId` (`prisma/schema.prisma:20`) stays in Prisma and is read by the Devis precedence (`lib/use-cases/devis.ts:180–188`), so the Client sits astride two systems.

**(c) No Medusa.** Cost zero. Set against that, what Medusa would add that eguidar lacks: a third-party-maintained admin (eguidar has one, with ADR-0026/0027/0029/0030 rules); transactional workflows with compensation (eguidar has `mutation-squelette` and Prisma transactions); a translation module (unneeded — one language); a search module (eguidar has Meilisearch with fault tolerance pinned by tests); returns/claims (eguidar has 6 statuses and restocking); multi-currency/multi-region (eguidar sells in MAD only). The three genuine gaps — index consistency is best-effort only, `brand` is a free string so there is no brand entity, and stock has no storage location — **none of them requires Medusa**.

**The honest cost centre.** Not the schema: it is `lib/use-cases/`, where nearly every module has a sibling `.test.ts` (`admin-catalog.test.ts`, `admin-structure.test.ts`, `search-suggestions-meili.test.ts`, `structure-user-facing.test.ts`, `meili-reglages.test.ts`, …). Any adoption story has to say what happens to that tested surface — that is the bill, and the ADRs named above are the specification it currently satisfies.

## 8. What is not answered / open questions

1. **Cycle guard (highest value).** Run a live Medusa 2.21.2 and `POST /admin/product-categories/{id}` with `parent_category_id` set to one of its own descendants; observe whether the request errors, hangs, or rewrites `mpath`. The claim here is a source read only.
2. **Price unit, empirically.** Create a price of `20.5` on a live instance and read both the API response and `price.amount`/`raw_amount` in PostgreSQL. This would settle the doc contradiction with an observation instead of a citation.
3. **`projectConfig.databaseSchema`.** Point Medusa at a dedicated schema in eguidar's database and run `medusa db:migrate`; confirm no `"user"` collision and that Prisma's migrations stay untouched.
4. **The community Meilisearch plugin in practice.** Pin `@rokmohar/medusa-plugin-meilisearch@^2.3.0` against Medusa 2.21.x, index a product, and observe whether `POST /store/search` honours publishable-key scoping and locale indexes as its README claims.
5. **CSV import of product metadata.** Export one product with a `Product Metadata` column (and a `specs`-shaped value) and see whether the importer accepts it — no such column was found in the documented set. (The `Product Category` id question is closed: the column takes ids, see §3.)
6. **Facebook auth.** Check the auth module's provider registry for a Facebook provider beyond the registered `emailpass`/`github`/`google`/`oidc` — eguidar's ADR-0019 depends on it.
7. **Admin extensions for Villes/Livraison.** Determine whether `admin/widgets` / `admin/ui-routes` can host eguidar's city-fee and threshold screens; the mechanisms exist, the case was not verified.
8. **Coolify (ADR-0020).** Check that Medusa's two processes plus PostgreSQL and Redis deploy there, and at what resource cost.
9. **Node patch level.** Compare the deploy image's Node 22 patch against `develop`'s `>=22.22.0` if the project tracks `develop` rather than the published tag.
10. **Store visibility of `is_active: false`.** Verify whether the Store API excludes inactive categories by default — the Store filter set does not expose the field, so this must be observed, not read.
