# Task-action refusals redirect through the mutation shell

The two order-refusal errors (`InvalidOrderTransitionError`, `OrderNotFoundError`) were the only domain errors that did not extend `UserFacingError`, because the mutation shell could not express "redirect to a refusal URL" — the only way a task action could honor them was a try/catch around `run` (the old `updateOrderStatusAction` pinned this rationale in its local catch, and a test title froze it in place). We decided that domain errors classify themselves as `UserFacingError` at their definition site, and that `adminTaskAction` accepts an optional `refusalUrl(input)` callback: when `run` throws a `UserFacingError`, the shell redirects to `refusalUrl(input)`; without `refusalUrl` the refusal stays a silent void (status quo). Parse failures never trigger the refusal redirect — they must not send the user to a detail page announcing a transition refusal that never happened — and the parse contract is total (`parse` returns `Input` or throws, never `null`), with `parseMoneyField`/`parseRequiredId` helpers absorbing the old `INVALID_FORM_MESSAGE` guards.

Considered options: keeping the try/catch in `run` (rejected — per-action boilerplate the shell exists to absorb); defaulting refusals to a redirect to `next` (rejected — silently changes every task action and loses the detail-page banner that names the refusal); adopting the form-action UX (error state in return value) for task actions (rejected — a bigger UI refactor with no gain for fire-and-forget actions).
